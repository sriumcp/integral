# B2 — Adapter #3 (GitHub issues as feature-campaign)

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Read GitHub issues for a configured repo and produce typed `feature-campaign` Intents that round-trip through `WorkspaceSchema`, with sub-issue hierarchy preserved as `decomposition.children`.

**Architecture:** Mirrors B1's transport/interpreter split. `GitHubIssuesSource` is the abstract transport (returns issues + parent→children edges); `GhCliIssuesSource` is the v0.1 Node-only impl invoking the `gh` CLI as a subprocess. The pure interpreter `buildFeatureWorkspace(source)` produces `feature-campaign` Intents and reconstructs the tree client-side from sub-issue references. Single paginated fetch for all repo issues; per-tracking-issue calls only when `subIssuesSummary.total > 0`.

**Tech Stack:** TypeScript strict + zod 4 + Vitest + `gh` CLI subprocess via Node's argv-based subprocess API (`execFile` family — never shell-string variants, since arguments are passed as a typed array with no shell interpretation).

---

## Goal

A user with a GitHub repo registered as a `kind: 'github-issues'` source in `integral.config.json` can:

1. Open Integral.
2. See the repo's issues on the Map as `feature-campaign` TreeCards alongside Nous/Coral.
3. Tracking issues (`subIssuesSummary.total > 0`) appear at the top level with their sub-issues as children; leaf issues appear at the top level as childless cards. Recursive nesting works (a sub-issue that's itself a tracking issue gets its own children).
4. Click into Detail → raw-field rendering of declaration + holder (assignees) + tags (labels) + repo_anchor.
5. Merged workspace with all three adapters (Nous + Coral + GitHub-issues) validates against `WorkspaceSchema`.

**Stop conditions:**

- `buildFeatureWorkspace(source)` produces a `Workspace` validating against `WorkspaceSchema` for any synthetic-fixture or real-repo input.
- Issue → `feature-campaign` mapping covers: title, body, labels, assignees, state, state_reason, created_at, repo coordinates.
- Sub-issue tree is preserved: parent's `decomposition.children = [child intent ids]`; sub-issues do NOT appear at the Map's top level.
- Cross-repo sub-issues (children whose repo doesn't match the configured source) are silently dropped (recorded as a gap; the parent's children list excludes them).
- `gaps.md` records every Feature-side schema-fit issue surfaced as G-F-1..G-F-N.
- Verification quintuple green: `test:run` + `typecheck` + `build` + `test:e2e` + `test:e2e:visual`.
- `roadmap.md` flips B2 to ✓ done; `CLAUDE.md` "Current state" updated; test counts bumped.

**Out of scope (deferred to v0.2):**

- `feature-pr` Intents (PRs need diff parsing + CI status — different shape entirely).
- Linked PRs as children of an issue (`Closes #123` references; the PR-API integration that resolves them).
- Comments → typed events. v0.1 doesn't load comments at all (one extra API call per repo would work, but mapping comments to `Operation`s requires deciding between `clarify` vs. dropping; deferred).
- `feature-campaign.inherited_conventions` populated from repo-CLAUDE.md walk. v0.1 emits `[]` with G-F-N gap.
- `feature-campaign.standing_invariants` populated from CI rules / lint configs. v0.1 emits `[]` with G-F-N gap.
- `feature-campaign.primary_pr_anchor` (no PR reading in v0.1). Field stays `undefined`.
- Cross-repo sub-issues (parent in repo A, child in repo B). v0.1 drops with gap.
- Task-list-syntax hierarchy (`- [ ] #123` in issue body, no formal sub-issue link). v0.1 honors only formal sub-issues.
- Writeback (open/comment/close issues from chrome). v0.2 with the orchestrator.
- Issue → PR linking (`Closes #X`). v0.2 with full feature-dev.
- Multi-repo per source. v0.1 = one source = one repo.
- Projection plugin for `feature-campaign`. Engine falls back to raw fields, same as Coral. v0.2 ships per-kind plugins.

## Why this scope

B1 (Coral) tested the schema's `coral-optimization` extension against real DAG-shaped data. B2 tests `feature-campaign` against real tree-shaped data with the additional novelty of a **networked source** — first non-filesystem transport. The substrate's `XSource` abstraction was always meant to admit non-fs sources; B2 is the load-bearing test of that.

The thinner scope (no PRs, no CI, no writeback) keeps B2 a falsification adapter rather than a full feature-dev integration. Full feature-dev is v0.2, designed once with the schema lessons of three other adapters in hand.

## Architecture

```
┌─────────────────────────────────────────────────────────┐
│ src/adapters/feature/  (browser-safe, pure)             │
│   types.ts          — GitHubIssuesSource, ParsedIssue   │
│   interpreter.ts    — buildFeatureWorkspace(source)     │
│   tree.ts           — parent → children reconstruction  │
│   index.ts          — public re-exports                 │
└─────────────────────────────────────────────────────────┘
                        │
                        ▼ (transport boundary)
┌─────────────────────────────────────────────────────────┐
│ vite-plugin-nous-adapter/                               │
│   gh-cli-source.ts          — Node-only, gh subprocess  │
│   sources-config.ts         — accept kind: 'github-issues'
│   index.ts                  — branch /api/workspace     │
└─────────────────────────────────────────────────────────┘
```

**Plugin location.** Same as B1: extend the existing `vite-plugin-nous-adapter/` directory. One config file, one source registry, one workspace cache. Document the historical name; v0.2 may rename when there's enough motivation.

**Why `gh` CLI over REST + PAT.**

- Reuses user's existing `gh auth login` (no new env-var management).
- `gh` handles rate-limit retry, secondary-rate-limit, and pagination automatically.
- Output is JSON; subprocess invocation uses Node's argv-based API (the variant that takes a literal command name plus a typed-string-array of arguments — argv is passed directly to the OS, not interpreted by a shell, so there is zero shell-injection surface).
- Cost: assumes `gh` is installed. Matches the existing assumption that users installing Integral are developer-shaped.
- v0.2 swaps to REST + PAT or adds non-GitHub hosts (Gitea, GitLab) as a separate transport class.

**Subprocess discipline.**

All `child_process` imports stay in `vite-plugin-nous-adapter/gh-cli-source.ts` — never in `src/`. Mirrors the LLM client architecture (Anthropic/OpenAI clients live outside `src/`; tests inject mocks at the `XSource` boundary).

The implementation MUST use the argv-based subprocess invocation (Node's `child_process.execFile` or its promisified variant), NOT the shell-string variant. The shell-string variant interprets its single string argument through `/bin/sh -c`, which would let any field of an issue body or label name break out into shell commands if interpolated. The argv variant takes the command name as a literal first argument and the remaining arguments as a typed string array passed verbatim to the OS — no shell, no injection. All `gh` arguments are statically composed (e.g., `--repo`, `--state`, `--limit`) plus the configured repo coordinate (validated against `^[a-zA-Z0-9._-]+/[a-zA-Z0-9._-]+$` before any subprocess call); user-controlled fields like issue body never reach the argv array.

### `IntentState` per issue

- `id` = `<intentId>-STATE`
- `intent_id` = `<intentId>`
- `status`: per state mapping below.
- `last_advanced_at`: `issue.closedAt ?? issue.updatedAt ?? issue.createdAt`.
- `last_advanced_by`: `issue.closedBy` Party if closed; else the most recent assignee or the issue author.
- `history`: `[]` (v0.1 doesn't reconstruct transition history; gap G-F-N).
- `external_anchors`: `[{kind: 'github-repo', uri: <issue.htmlUrl>, read_only: true}]`.

### State mapping

| GitHub `state` | GitHub `stateReason` | Schema `Status` |
|---|---|---|
| `OPEN` | * | `'active'` |
| `CLOSED` | `COMPLETED` | `'satisfied'` |
| `CLOSED` | `NOT_PLANNED` | `'abandoned'` |
| `CLOSED` | `DUPLICATE` | `'abandoned'` |
| `CLOSED` | `REOPENED` | `'active'` (rare; transient) |
| `CLOSED` | `null` (legacy) | `'satisfied'` (best-guess; G-F-N gap) |

### Holder mapping

GitHub issues have multiple assignees (humans). v0.1 maps:

- Each assignee → `Party { id: 'github-user:<login>', kind: 'human', display_name: <login> }`.
- Multiple assignees → `holder.mode = 'human-held'`, parties = list of all.
- Zero assignees → synthetic single-party fallback: `{ id: 'github-unassigned', kind: 'system', display_name: '(unassigned)' }`, `mode = 'jointly-held'`. The schema's `Holder.parties.min(1)` requires at least one; the synthetic placeholder is a v0.1 lossy mapping (G-F-N) — v0.2 may distinguish "unassigned" from "abandoned" with a typed sentinel.

## Sub-issue tree construction

### The algorithm

Pseudo-code (the actual implementation in `tree.ts` is a bit fussier with edge cases):

```
1. Fetch all issues in repo (one paginated call).
2. For each issue I where I.subIssuesSummary.total > 0:
   - Fetch /sub_issues for I.
   - Filter children: drop any whose repository URL ≠ source's repository URL.
   - Record (I.number → [child.number, ...]) in childrenByParent map.
3. Compute parentOf map by inverting childrenByParent.
4. Build Intent[] from issues, where:
   - intent.decomposition.children = childrenByParent.get(issue.number).map(intentIdFor)
5. Top-level Map placement is implicit: an Intent appears at top of Map iff
   no other Intent's decomposition.children contains its id. The interpreter
   doesn't compute "rootness" — it just emits accurate decomposition edges
   and lets MapSurface filter for orphans.
```

### Cross-repo handling

The `/sub_issues` endpoint may return issues from other repos (rare but legal). We compare each child's repository URL against the source's `<owner>/<repo>` and silently drop mismatches. Recorded as G-F-N. The parent's children list excludes them entirely; consumers can't tell from the workspace alone that the parent had additional cross-repo children.

### API call counting

- 1 call: `gh issue list --repo <owner>/<repo> --state all --limit <N> --json ...` (paginated by `--paginate` flag if N > 100; default `--limit` is 30 so set explicitly to 1000 for v0.1).
- K calls: one per tracking issue, where K = count of issues with `subIssuesSummary.total > 0`.

For a typical repo (100 issues, 5 tracking issues): 6 API calls total. Acceptable.

### Cycle defense

GitHub disallows sub-issue cycles structurally (you can't make A a child of B if B is already a child of A). But the algorithm shouldn't trust the data: if a cycle appears in the `childrenByParent` map, the tree-reconstruction code MUST NOT infinite-loop. The implementation uses a visited-set during traversal; cycles produce a workspace where each cycle member has the other in its `decomposition.children`. Schema-valid (the bijection invariant is per-record); the chrome's tree-rendering may render oddly. Test 8 in `tree.test.ts` covers this defensively.

## Schema fit — surfaces I expect to see (G-F-1..G-F-N)

Pre-recorded so the gap-tracking discipline is on rails before the code lands. Numbers may shift as we encounter actual data.

- **G-F-1.** `Declaration.success_criterion` has no source in a GitHub issue. Same shape as G-N-8 (Nous) + G-C-1 (Coral). **Three adapters now want this** — strongest signal yet that it should be optional or removed in v0.2's schema bump.
- **G-F-2.** `feature-campaign.inherited_conventions` requires a non-empty array per the schema's `z.array(KnowledgeRefSchema)` — actually it's just `z.array`, defaults allow empty. Verify; if min(1) sneaks in elsewhere, gap-record.
- **G-F-3.** `feature-campaign.standing_invariants` similarly. Both populated as `[]` in v0.1; v0.2 walks repo-CLAUDE.md / CI configs.
- **G-F-4.** `state_reason: REOPENED` is a *transient* state (the issue is currently open). Schema's `Status: active` swallows the reopen-history. v0.2 candidate: history reconstruction from the timeline events API.
- **G-F-5.** `state: CLOSED` with `stateReason: null` (legacy issues closed before stateReason existed). v0.1 maps to `'satisfied'` defensively. v0.2 may want to disambiguate.
- **G-F-6.** Unassigned issues require a synthetic `(unassigned)` Party to satisfy `Holder.parties.min(1)`. v0.2: relax to allow zero parties on `feature-campaign`, OR introduce a typed "unassigned" sentinel.
- **G-F-7.** `IntentState.history` is empty — GitHub timeline events (assigned/unassigned, label add/remove, milestone change, etc.) aren't reconstructed. v0.2 walks `/timeline`.
- **G-F-8.** Comments are not loaded. Activity strip on Detail for `feature-campaign` shows only state transitions (zero in v0.1 since history is empty). v0.2: load via `/issues/{n}/comments` or repo-wide `/issues/comments`, map to `clarify` operations.
- **G-F-9.** Cross-repo sub-issues are silently dropped. v0.2: multi-repo source semantics, OR cross-repo `EvidenceLink`s.
- **G-F-10.** `ExternalAnchorKindSchema` doesn't include `'github-repo'`. **B2 adds it as a v0.1.0 additive amendment** (per CLAUDE.md: "Optional additive fields do not bump the version" — adding an enum value is structurally analogous and stays at v0.1.0). Document the addition in `intent-schema-v0.1.md`.
- **G-F-11.** `feature-campaign.repo_anchor` works for one repo per source. Multi-repo workflows (monorepo with sub-repos, cross-org issue tracking) need a different shape. v0.2 candidate.
- **G-F-12.** Issue → PR linking (`Closes #X` references in PR bodies, `linked_pr` field) is unrepresented. v0.2 with full feature-dev.
- **G-F-13.** Task-list syntax (`- [ ] #123` in issue body) is unrepresented. Many older repos use this exclusively. v0.2: parse and map to `decomposition.children`.

## Risk & escape valves

- **`gh` not installed on user's machine.** The argv-based subprocess invocation throws `ENOENT`. Catch in `gh-cli-source.ts`, surface as a structured error: "gh CLI not installed; install via https://cli.github.com or set kind: 'nous'/'coral' instead." The Vite plugin returns 500 with the message; the chrome's per-source partial-success path keeps other sources working.
- **`gh` not authenticated.** `gh issue list` exits non-zero with stderr explaining auth failure. Catch and surface similarly.
- **Rate-limit hit.** `gh` retries automatically; if it gives up, the call returns non-zero. Treat as transient; recommend waiting; surface to user. v0.2 may add longer backoff.
- **Issue with malformed JSON in `gh` output (shouldn't happen but).** `JSON.parse` throws; the per-source error path catches; log, return 500.
- **Issue body with embedded null bytes / control chars / extreme unicode.** `gh` returns valid JSON; zod's `string` accepts any unicode; clamp via slice.
- **Issue title >> 80 chars.** Same shape as B1's spec-gaming attempt — clamp to 77 + ellipsis.
- **Subprocess timeout.** Large repos (10K+ issues) may take seconds. The argv-based subprocess API supports a `timeout` option; set 60s in v0.1; surface `ETIMEDOUT` gracefully.
- **`subIssuesSummary` not present (older API responses, very old repos).** Default to `{total: 0}`; treat as leaf. Test 2 covers this.
