# A5 — Run command surfacing (revised, simpler)

Plan for the last piece of Track A: surfacing the exact `nous run` command in the chrome so the user can execute it from their terminal without re-deriving paths or flags.

Companion to `roadmap.md § A5`. **This plan deliberately scopes A5 down** from the roadmap's original framing (spawn processes from the chrome) to a smaller goal (surface the command). The orchestration story — actually invoking and tracking the process from inside Integral — is deferred to v0.2 where it can be designed alongside an orchestrator and not bolted onto a button.

---

## Goal

After A4 + A4.6, the user has shaped a campaign and the YAML is on disk. To run it, they currently have to:
1. Remember which Nous source's path the campaign was written to.
2. Look up the campaign's run_id.
3. Type `cd <path> && nous run --auto-approve campaign-<runId>.yaml` correctly.

A5 closes that gap. The Detail surface for a `nous-campaign` whose state is `active` or `gated` shows the exact command (with absolute path), copyable to clipboard. The user runs it from their terminal. Existing workspace refresh picks up iterations as Nous produces them.

**Stop conditions:**
- Detail surface for an `active` or `gated` `nous-campaign` shows a `run command` panel.
- Panel contains the absolute working directory + `nous run --auto-approve campaign-<runId>.yaml`.
- A copy-to-clipboard button copies a single-line, shell-correct version of the command.
- The panel is hidden for any other intent kind, and for any state where running doesn't make sense (`draft`, `satisfied`, `revoked`, `abandoned`).
- Existing workspace refresh (A3) picks up iterations Nous writes.

---

## Why this scope, not the original A5

The original A5 framing — "▶ run" button on the chrome that spawns `nous` via `child_process.spawn` — pulled Integral toward platform-shape: process-manager-as-component, PID-file dance, polling endpoints, kill semantics. None of that is wrong as software, but all of it conflicts with the substrate's protocol-first posture (`CLAUDE.md`: "does not host execution").

The simpler design honors the principle:
- **Integral does what only it can do**: resolve a typed Intent → exact shell command, given knowledge of the source registry, the runId, and the campaign-yaml location convention. The user can't easily do this without Integral.
- **The user does what the user does well**: run shell commands and track processes. They already have a terminal, `ps`, `Ctrl-C`, and shell history. Re-implementing those affordances in a browser polling endpoint adds complexity without value.

The orchestration story (a real "run from chrome" capability) returns in v0.2, designed alongside a workspace-watcher / orchestrator that can fire across all adapter kinds, not just Nous. By deferring, we avoid the bolt-on shape of "button per kind that knows how to spawn."

---

## Architecture — one component, no server

The whole feature is browser-side and pure:

```
┌──────────────────────────────────────────────────┐
│ <RunCommand intent={...} state={...}             │
│             registry={...} />                    │
│ Detail surface conditional render.               │
└──────────────────────────────────────────────────┘
                        │
                        ▼
┌──────────────────────────────────────────────────┐
│ runCommandFor(intent, state, registry)           │
│ Pure function. Returns                           │
│   { cwd, argv, oneLiner } | null                 │
│ Per-kind dispatch via a small registry           │
│ (only nous-campaign in v0.1).                    │
└──────────────────────────────────────────────────┘
```

No new endpoints. No process tracking. No state on the Vite plugin. The source registry's filesystem path (already exposed via `/api/sources`) is everything we need.

### Kind-pluggability

The dispatcher is shaped like the existing projection plugins, so v0.2 can drop in additional kinds without touching the chrome:

```ts
type RunCommandPlugin = (
  intent: Intent,
  state: IntentState,
  source: SourceEntry
) => RunCommand | null

const plugins: Partial<Record<IntentKind, RunCommandPlugin>> = {
  'nous-campaign': nousRunCommand,
  // v0.2: 'coral-optimization': coralRunCommand,
}
```

Each plugin returns `null` if the intent isn't ready to run (state mismatch, missing fields, kind doesn't yet have a runner). The component renders nothing in that case.

## The UI affordance

A small panel that lives in the Detail surface body for `nous-campaign`s when `runCommandFor` returns non-null. Visual posture matches the existing chrome (mono font, paper background, soft border):

```
┌─────────────────────────────────────────────────────────┐
│ to advance this campaign, run from your terminal:       │
│                                                         │
│   cd /Users/sri/Documents/Projects/inference-sim        │
│   nous run --auto-approve campaign-foo-bar.yaml         │
│                                                         │
│                                              [⧉ copy]   │
│                                                         │
│ then click ↻ refresh above to see iterations.           │
└─────────────────────────────────────────────────────────┘
```

The two-line display is for readability. The `[⧉ copy]` button copies a single-line, shell-quoted version (`cd '<cwd>' && nous run --auto-approve <yaml>`) so paste-and-run works.

**Where in DetailSurface:** between `ProjectionSection` and `ChildrenSection`. Visible at structure and detail zoom; hidden at overview (which isn't reachable from Detail today, but reserve the rule).

## Mapping intent → command

A `nous-campaign` Intent carries enough structure to derive the command:
- `intent.provenance.source` → sourceId. Look up in registry → `sourcePath`.
- `intent.id` follows the convention `nous:<source-slug>:<runId>` (per `interpreter.ts:271-276`); we extract `runId` from the third colon-separated segment, NOT by re-slugging the path.
- The yaml path is `<sourcePath>/campaign-<runId>.yaml` by Nous convention.

Edge cases that return `null` (panel hidden):
- `intent.kind !== 'nous-campaign'`.
- `state.status` is not `active` or `gated`.
- `intent.provenance.source` doesn't resolve in the registry.
- `intent.id` doesn't match the `nous:*:*` shape (e.g., a fixture intent).

---

## Shell quoting

The one-liner needs to handle paths with spaces and unusual characters. Strategy: single-quote-wrap with `'\''` escape for embedded single quotes. Standard POSIX-safe pattern:

```ts
function shellQuote(s: string): string {
  return `'${s.replace(/'/g, `'\\''`)}'`
}
```

Output: `cd '/Users/sri/My Stuff/inference-sim' && nous run --auto-approve 'campaign-foo.yaml'`.

We don't need to handle Windows shell semantics (Integral is dev-only, and Nous is *nix-targeted).

## TDD plan

All tests are pure or RTL behavioral. No process spawning, no real LLMs.

**`run-command.ts` (pure):**
1. `runCommandFor` returns `null` for non-Nous kinds.
2. Returns `null` for Nous kinds in `draft`, `satisfied`, `revoked`, `abandoned`.
3. Returns a populated `RunCommand` for `active` Nous campaigns.
4. Returns a populated `RunCommand` for `gated` Nous campaigns.
5. Returns `null` when the source isn't in the registry.
6. Returns `null` when the intent id doesn't match the `nous:*:*` shape.
7. Extracts `runId` correctly from intent ids with hyphens in the source slug.
8. `shellQuote` produces single-quoted output.
9. `shellQuote` correctly escapes embedded single quotes.
10. The one-liner concatenates `cd <quoted-cwd> && <argv>` with spaces handled.

**`RunCommand.tsx` (RTL):**
1. Renders nothing when `runCommandFor` returns `null`.
2. Renders the cwd and the nous argv when populated.
3. Copy button calls `navigator.clipboard.writeText` with the one-liner.
4. After copy, the button shows `copied ✓` for ~2s then reverts.
5. On `navigator.clipboard` failure, falls back to a textarea-select strategy and surfaces no error to the user.
6. Hint line ("then click ↻ refresh") is present for screen-reader continuity.

## What this defers to v0.2

The roadmap's original A5 framing — execution from inside the chrome — is deferred. The deferred work, when it returns, should be designed at the *substrate* level, not as a bolt-on:

- **Orchestrator service.** A workspace-watcher that observes intent state and fires runs based on policy. Single concurrent run per campaign, multi-campaign queue, auto-restart on transient failure. Probably its own long-lived Node process, not the Vite plugin.
- **Runner abstraction across kinds.** Nous, Coral, GitHub-issue feature-dev — each with its own invocation. Designed once, shared.
- **Filesystem auto-watch.** Replace the `↻ refresh` button with a chokidar-based watcher that triggers re-reads on `.nous/<run>/` writes. Then the round-trip really does close inside the chrome.
- **Process control surfaces.** Status, logs, kill — only meaningful once execution lives inside Integral.

By scoping A5 to "surface the command," we get a clean v0.1 stop point, the substrate stays protocol-shaped, and v0.2's orchestrator design isn't pre-committed by a button-per-kind UI.
