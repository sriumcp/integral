# B1 — Adapter #2 (Coral)

Plan for the second of three Track B falsification adapters. Read a Coral project directory and produce typed `coral-optimization` + `coral-attempt` intents that round-trip through `WorkspaceSchema`.

Companion to `roadmap.md § B1`. **Phases 1+2 minimum** — read declarations + scored attempts. No operations diff. No writeback. The Phase-4 ops engine (`src/lib/workspace-diff.ts`) is generic and adapter-agnostic; Coral's job in v0.1 is to produce a clean static snapshot, not to test the diff.

---

## Goal

A user with `~/Documents/learning/coral/pi-mc/` registered as a Coral source in `integral.config.json` can:
1. Open Integral.
2. See pi-mc's run (`results/pi-mc/2026-05-24_194843/`) appear on the Map as a `coral-optimization` TreeCard, alongside any Nous campaigns.
3. Click into Detail and see two `coral-attempt` children rendered structurally (raw-field fallback for now — projection plugins are v0.2).
4. The merged workspace validates against `WorkspaceSchema`, including the spec-gaming attempt that hit the 1e12 cap.

**Stop conditions:**
- `buildCoralWorkspace(source)` produces a `Workspace` validating against `WorkspaceSchema` for the pi-mc fixture (1 campaign + 2 attempts).
- The DAG edge from `parent_hash` is captured (each child attempt has its parent attempt's id in `extension.parent_attempts`).
- A multi-source workspace with both `nous` (inference-sim) and `coral` (pi-mc) enabled validates as a single merged `Workspace`.
- `gaps.md` records every Coral-side schema-fit issue surfaced during implementation (G-C-* prefix).
- `npm run test:run` + `typecheck` + `build` + `test:e2e` all exit 0.
- Visual baselines unchanged unless we deliberately add a new TreeCard variant; if `coral-optimization` from a real adapter renders distinguishably, regen the baselines and document.

**Out of scope (deferred, with rationale below):**
- Phase-4 operations diff (G-N-style adapter-emitted ops). Coral can wait — diffWorkspaces is already proven against Nous's tree shape; Coral's DAG shape will be a useful second test, but not v0.1-blocking.
- Writeback. No "▶ run coral" affordance — `coral` is a CLI in someone else's repo, and we don't yet shape coral drafts. v0.2 with the orchestrator.
- Projection plugin for `coral-optimization` / `coral-attempt`. The engine falls back to raw fields when no plugin matches; v0.2 ships per-kind plugins as part of semantic-model expansion.
- Notes-body dereferencing. KnowledgeRefs surface as count rows (analogous to Nous principles) — opaque URIs, no markdown rendering. v0.2 with G-N-2 promotion.
- Persona / skill rendering (`agents/*.md`, `skills/<skill>/`). These are sub-systems Coral expects UI-side. v0.1 ignore + record gaps.
- Diagnostics / heartbeat / logs / sessions. Pure operational state; no schema home.

---

## Why this scope, not "full Coral"

Coral's `.coral/public/` tree carries 12 sub-directories (`attempts/`, `notes/`, `roles/`, `agents/`, `skills/`, `diagnostics/`, `heartbeat/`, `logs/`, `eval_logs/`, plus loose files). Two of them — `attempts/` and `notes/` — fit existing schema fields directly (`coral-attempt` extension + KnowledgeRef). The rest are speculative shape: the schema doesn't yet know about persona role-evolution histories, reusable skill bundles, or per-agent log streams.

The right v0.1 falsification move is to **read what fits cleanly and record what doesn't**. The schema's `CoralAttemptExtension.parent_attempts: list[IntentId]` is already plural, which means the DAG fits at the type level via the extension — no schema bump needed. That's the load-bearing v0.1 hypothesis. If `parent_attempts` *had* been singular, B1 would have surfaced a v0.2 schema bump on day one. It's plural, so we get to test the next layer (chrome rendering of DAG-shaped children) without first paying for a schema change.

## Architecture — mirror Nous's transport/interpreter split

```
┌─────────────────────────────────────────────────────────┐
│ src/adapters/coral/  (browser-safe, pure)               │
│   types.ts          — CoralSource, ParsedAttempt, etc.  │
│   interpreter.ts    — buildCoralWorkspace(source)       │
│   notes.ts          — notes/*.md → KnowledgeRefs        │
│   index.ts          — public re-exports                 │
└─────────────────────────────────────────────────────────┘
                        │
                        ▼ (transport boundary)
┌─────────────────────────────────────────────────────────┐
│ vite-plugin-nous-adapter/                               │
│   coral-filesystem-source.ts  — Node-only fs walker     │
│   sources-config.ts           — accept kind: 'coral'    │
│   index.ts                    — branch /api/workspace   │
└─────────────────────────────────────────────────────────┘
```

**Plugin location decision: extend the existing `vite-plugin-nous-adapter/` directory; do NOT spin up a new plugin.** Rationale:

1. The directory is already a multi-adapter zoo (writeback, shape, projection, sources-config). Adding `coral-filesystem-source.ts` alongside `filesystem-source.ts` is the same kind of additive change.
2. One Vite plugin = one config-file load + one set of HTTP middleware. Splitting would duplicate `loadSourcesConfig`, `/api/sources`, and the workspace cache for no benefit.
3. The plugin's name (`name: 'nous-adapter'` in the Vite Plugin object) is internal-only — we leave it as-is and document the historical name in the file header. v0.2 with adapter #3 (B2: GitHub issues) is the right time to rename if we want.
4. The browser side already abstracts: `SourceEntry.kind` is `'fixture' | 'adapter'`; the *adapter kind* (nous/coral) is server-only. So no churn in `src/lib/sources.ts`.

**Transport/interpreter discipline:** the same as Nous. `CoralSource` is the abstract transport (returns raw bytes for one run); `buildCoralWorkspace(source)` is the pure interpreter. `FilesystemCoralSource` is the only v0.1 concrete transport; v0.2 adds `S3CoralSource` etc. without touching the interpreter. Pure interpreters are the contract; tests target `buildCoralWorkspace` with synthesized `CoralSource` mocks (no fs).

## Mapping — Coral on-disk → typed Intents

### Source path semantics

`integral.config.json` source `path` points at the **Coral project root** (the dir with `task.yaml` + `seed/` + `grader/` + `results/`). The adapter scans `<path>/results/<task-name>/<timestamp>/` to discover **runs**.

```
<root>/                                    ← integral.config.json source.path
├── task.yaml                              ← read for grader/agents/direction
├── seed/, grader/                         ← untouched by adapter
└── results/<task-name>/<timestamp>/       ← one *run* per timestamp dir
    └── .coral/public/
        ├── attempts/<commit-sha>.json
        ├── notes/index.md + notes/experiments/*.md
        └── roles/agent-N.md
```

Multiple runs of the same task = multiple independent `coral-optimization` intents. Re-running `coral` from scratch makes a new timestamp dir — Coral runs share no state.

### `IntentState` (one per intent)

For both kinds:
- `id` = `<intentId>-STATE`
- `intent_id` = `<intentId>`
- `status`:
  - **Campaign:** always `'active'` (Coral has no run-level "done" signal we can read; the run might be ongoing or abandoned, the filesystem doesn't say). **Gap G-C-5.**
  - **Attempt:** `attempt.status === 'improved'` → `'satisfied'`; everything else → `'active'`. **Gap G-C-6** — full Coral status enum is unknown; `'improved'` is the only observed value.
- `last_advanced_at`: campaign = `lifetime.started_at`; attempt = `attempt.timestamp`.
- `last_advanced_by`: campaign = `CORAL_ORCHESTRATOR_AGENT`; attempt = the agent party.
- `history`: `[]` (we don't synthesize transitions in v0.1).
- `external_anchors`:
  - Campaign: `[{kind: 'coral-shared-dir', uri: 'file://<run>/.coral/public/', read_only: true}]`.
  - Attempt: `[{kind: 'coral-shared-dir', uri: 'file://<run>/.coral/public/attempts/<sha>.json', read_only: true}]`.

### DAG construction (the load-bearing test)

Pseudo-code:

```ts
// 1. parse all attempt JSONs in attempts/
const attempts = readAttempts()  // [{commit_hash, parent_hash, ...}]

// 2. build commit_hash → intent_id map
const byCommit: Map<string, string> = new Map()
for (const a of attempts) byCommit.set(a.commit_hash, makeAttemptId(campaignId, a.commit_hash))

// 3. for each attempt, resolve parent → parent_attempts + decomposition wiring
const childrenOf: Map<string, string[]> = new Map()  // parent intent id → child intent ids
const rootAttempts: string[] = []
for (const a of attempts) {
  const myId = byCommit.get(a.commit_hash)!
  const parentId = byCommit.get(a.parent_hash)  // undefined if parent_hash is the seed root
  if (parentId) {
    const list = childrenOf.get(parentId) ?? []
    list.push(myId)
    childrenOf.set(parentId, list)
  } else {
    rootAttempts.push(myId)
  }
}

// 4. campaign.decomposition.children = rootAttempts
// 5. each attempt's decomposition.children = childrenOf.get(myId) ?? []
// 6. each attempt's extension.parent_attempts = parentId ? [parentId] : []
```

The schema admits this — `decomposition.children` is `IntentId[]` and an attempt is just another `Intent`. The DAG semantics live in `parent_attempts` (typed plural for forward compatibility); the tree spine via `decomposition.children` lets the Map's TreeCard render without recursive indirection.

## Gap entries to record in `gaps.md`

These get appended under a new section `## Source: Coral optimization sizing` with anchors to the pi-mc fixture path. Records as we encounter them — no silent schema amends.

- **G-C-1.** `Declaration.success_criterion` has no source in `task.yaml`. Same shape as G-N-8. Lossy: emit `''`. v0.2: relax field to optional or add a Coral-specific source.
- **G-C-2.** `direction: maximize|minimize` (from `task.yaml.grader.direction`) has no home on `CoralOptimizationExtension`. Lossy: stuffed into `tags` as `direction:maximize`. v0.2 candidate: add `direction: 'maximize' | 'minimize'` to the extension.
- **G-C-3.** `search_algorithm` enum doesn't reflect Coral's actual mechanism. The task.yaml doesn't carry one; Coral's code does (best-of-N over N parallel agents per generation). Lossy: emit `'other'`. v0.2: extend enum or accept free-form `string`.
- **G-C-4.** `roles/agent-N.md` carries rich role-evolution history (generation, last_revised_after_eval, narrative sections, history log). The schema's `Party` is `{id, kind, display_name}` only. Lossy: drop everything but `agent_id`. v0.2 candidate: surface role frontmatter as a `KnowledgeRef` on the agent (requires a Party-scoped knowledge concept that doesn't yet exist).
- **G-C-5.** No campaign-level "done" / "satisfied" signal. A Coral run that hit max score is structurally identical on disk to a Coral run that ran out of budget. v0.2 candidate: surface a `<run>/.coral/public/state.json` analogous to Nous, OR derive run status from "no new attempts in N hours" heuristic (chrome-only, not adapter).
- **G-C-6.** `coral-attempt.status` enum is unknown. Observed: `'improved'`. Likely also `'regressed'`, `'failed'`, `'pending'`. v0.1 maps `improved → satisfied`, default → `active`. v0.2: nail down full enum from Coral source + add explicit per-Coral-status mapping.
- **G-C-7.** `attempt.feedback` is empty in the fixture but has no schema home. v0.2 candidate: add `evaluator_feedback: string?` to `CoralAttemptExtension`.
- **G-C-8.** `attempt.shared_state_hash` checksums the shared knowledge corpus at the moment of the eval. Useful for "which set of notes was this attempt seeded with" — but the schema has no concept of corpus snapshotting per attempt. v0.1 drops. v0.2 candidate: add a `corpus_snapshot_hash` field on `CoralAttemptExtension`.
- **G-C-9.** `attempt.metadata.budget_class` (observed `'real'`; Coral also has `'tune'`). v0.1 stuffed into `tags`. v0.2: typed `budget_class` field on extension.
- **G-C-10.** `notes/**.md` mapping to `KnowledgeRef` is lossy in the same shape as Nous principles (G-N-2). URI scheme `coral-note://<source>/<task>/<timestamp>/<rel-path>`; full markdown body dropped. v0.2: same resolution as G-N-2 (typed `Note`/`Principle` object with mechanism, confidence, evidence list, etc.).
- **G-C-11.** Personas in `agents/<persona>.md` (e.g., `deep-researcher`, `librarian`) are pre-installed reusable agent definitions. v0.1: ignore. v0.2 candidate: typed `Persona` concept; pre-installed personas inherit into a `coral-optimization` campaign as `KnowledgeRef`s of role `'methodology'`.
- **G-C-12.** Skills in `skills/<skill>/SKILL.md + scripts/ + references/` are reusable capability bundles. v0.1: ignore. v0.2 candidate: typed `Skill` concept; same shape as personas. Strongly correlated with `KnowledgeRoleSchema`'s existing `'skills'` value, which suggests the schema already anticipates this.
- **G-C-13.** `diagnostics/`, `heartbeat/`, `logs/`, `eval_logs/`, `eval_count`, `sessions.json`, `grader_daemon_heartbeat` are operational state with no schema home. v0.1: drop. v0.2: probably stays out of the schema (these are observability concerns, not intent semantics).
- **G-C-14.** Each agent gets a real git worktree at `<run>/agents/<agent_id>/.git`. The schema's `worktree_anchor: ExternalAnchor` is the right shape, but the `kind` enum doesn't include `'git-worktree'` — closest is `'worktree'` (which we use). Lossy because we lose the per-attempt commit hash from the agent's git history (the attempts JSON has `commit_hash` but it's the eval commit, not necessarily the agent's tip). v0.2: confirm or add `'coral-agent-worktree'` kind.

(Numbering picks up after the existing 12 G-N entries.)

## TDD plan

All tests are pure, except the `FilesystemCoralSource` test which writes a temp directory and reads it back. No real LLMs anywhere (per CLAUDE.md § Test discipline — adapters don't call LLMs at all in v0.1).

### `src/adapters/coral/interpreter.test.ts` — pure, ~25 tests

Synthesize a `CoralSource` mock that returns canned bytes per run.

**Empty / degenerate:**
1. Source with `listRunIds() = []` → `Workspace { intents: [], states: [], evidence_links: [], operations: [] }`. Validates against `WorkspaceSchema`.
2. Source with one run that has no `task.yaml` → run is skipped; empty workspace.
3. Source with one run that has `task.yaml` but no `attempts/` files → campaign emitted, zero children, `decomposition.children = []`. Validates.
4. Run with malformed `task.yaml` (parse error) → run skipped (mirrors Nous's malformed-yaml policy).

**Single-attempt mappings:**
5. One run + one attempt → 1 campaign + 1 attempt. Both validate. `campaign.decomposition.children = [attemptId]`. Attempt's `extension.parent_attempts = []` (parent_hash unresolved). Attempt's `decomposition.children = []`.
6. Attempt id format: `coral:<source-slug>:<task>:<timestamp>:attempt:<sha8>`.
7. `attempt.score` flows to `extension.score`.
8. `attempt.status === 'improved'` → state.status = `'satisfied'`.
9. `attempt.status === 'unknown-value'` → state.status = `'active'` (default).
10. Attempt with `metadata.budget_class === 'real'` → tags include `'budget-class:real'`.
11. Attempt without `metadata.budget_class` → tags empty.

**DAG-shaped attempts (load-bearing):**
12. Two attempts where B's `parent_hash === A.commit_hash` → A's `decomposition.children = [B-id]`; B's `decomposition.children = []`; B's `extension.parent_attempts = [A-id]`; campaign's `decomposition.children = [A-id]` (only the root).
13. Three attempts forming a chain (A → B → C) → exactly the chain wired; campaign's children = `[A-id]`.
14. Three attempts forming a Y (A → B, A → C) → A's children = `[B-id, C-id]`; campaign's children = `[A-id]`.
15. Two independent root attempts (both with parent_hash → seed) → campaign's children = `[A-id, B-id]`; both have empty parent_attempts.
16. Attempt with `parent_hash` matching no other attempt (the typical seed-pointer case) → treated as root; `parent_attempts = []`.

**Multiple runs:**
17. Two runs of same task at different timestamps → two independent campaigns with distinct ids; no cross-run edges.
18. Run timestamps parse from dir name format `YYYY-MM-DD_HHMMSS` → `lifetime.started_at` is correctly RFC3339.

**task.yaml extraction:**
19. `task.yaml.task.description` flows to `declaration.summary`.
20. `task.yaml.task.name` flows into the campaign id and title.
21. `task.yaml.agents.count = 2` → `extension.population_size = 2`. Missing → defaults to 1.
22. `task.yaml.grader.direction = 'maximize'` → `tags` includes `'direction:maximize'`. `'minimize'` → `'direction:minimize'`. Missing → `'direction:maximize'` default + a console.warn (or just no tag and gap-recorded).

**best_score_so_far:**
23. With direction=maximize and scores `[100, 50, 200]` → `best_score_so_far = 200`.
24. With direction=minimize and scores `[100, 50, 200]` → `best_score_so_far = 50`.
25. With zero attempts → `best_score_so_far` undefined.

**Fixture round-trip (the falsification anchor):**
26. The pi-mc fixture (synthesized in `__tests__/fixtures/pi-mc.ts` with the two real attempts inlined as TS literals) → buildCoralWorkspace produces 1 + 2 intents + 3 states; the workspace validates against `WorkspaceSchema`; both attempts (including the spec-gaming one with score=1e12) parse without error.

## Risk & escape valves

- **If a real attempt JSON has fields not in our `ParsedAttempt` shape:** the parser uses `[key: string]: unknown` to tolerate. We don't strictly schema-validate the input — that's the whole point of the lossy-mapping discipline.
- **If `parent_hash` cycles** (shouldn't happen in real Coral, but): the DAG construction is iterative (no recursion), so a cycle just produces a graph where two attempts reciprocally include each other's id in `decomposition.children`. The `WorkspaceSchema.refine` for the 1:1 bijection is per-intent, not graph-shape — cycles validate at the schema level. The chrome's tree-rendering would loop, but that's a chrome bug to surface in v0.2 if it ever happens with real data. We don't pre-empt.
- **If the spec-gaming attempt fails to validate** (the original reason this fixture was chosen): investigate immediately. Likely culprit: title length > 80 (the math.pi attempt's title is 90 chars). Adapter must clamp titles like the Nous adapter does, and the clamp is part of the spec.
- **If the timestamp-from-dirname parser fails:** fall back to dir mtime via `fs.stat`. Both interpretCampaign and CampaignFiles already do this for Nous (`campaignYamlMtime`); we mirror.
