## Concrete observations grouped by theme

### A. The "lossy fallback" tier is publicly visible

**Evidence:** `09-detail-feature-leaf.png`

- The SUMMARY card on Detail has a small `raw` toggle in its header — the projection-fallback affordance is exposed publicly. For Coral and GitHub-issues kinds this never goes away, because no projection plugin exists for them.
- The summary text reads `"Visual baseline regen tracker — Top-level leaf issue. Tracks…"` — title concatenated as a prefix to the body. Dumb fallback because no plugin is doing real work.
- Bottom card `0 invariants · repo` is bare (G-F-2/G-F-3 — `inherited_conventions` and `standing_invariants` empty for v0.1).

**v0.1.5 lever:**
- (a) Ship per-kind projection plugins for Coral + GitHub-issues — kills the asymmetry but is real engineering work (~2-4 days of LLM-prompt-design + caching + test coverage). Promotes S-1 in `semantics-v0.1.md`.
- (b) Redesign the fallback affordance to read as deliberate raw view rather than missing feature. Pure chrome work.

The decision frames how v0.1.5 relates to v0.2: option (a) folds part of v0.2's S-1 expansion into v0.1.5; option (b) defers all of it.

### B. Activity strip is silent for GitHub Intents

**Evidence:** `09-detail-feature-leaf.png` right panel reads `"no activity for this intent yet"`

- `IntentState.history = []` for GitHub Intents (G-F-7 — timeline events not reconstructed).
- Comments not loaded (G-F-8).
- The Activity Strip is dead weight on every GitHub Detail in v0.1.

**v0.1.5 lever:**
- (a) Load timeline+comments — promotes G-F-7 + G-F-8 from candidate to v0.1.5 commitment. ~1 day of work; one repo-wide call for comments + per-issue timeline (or repo-wide events) + map-to-clarify operations.
- (b) Make the empty state per-source-honest: "GitHub timeline events arrive in v0.2." Acknowledges the gap rather than hiding it.

### C. Stale-data signal missing for external sources

**Evidence:** `10-map-github-only.png` header reads `"5 active · 0 awaiting you"` — but #2 (B1) and #3 (B2) are now closed/satisfied. Counts should be `"3 active · 2 satisfied"`.

- Cause: the Vite plugin's `workspaceCache` (in `vite-plugin-nous-adapter/index.ts`) caches per source ID. Nous/Coral cache invalidates on writeback; GitHub-issues cache only invalidates on dev-server restart.
- The chrome has no way to detect external state drift on GitHub data.

**v0.1.5 lever:** add a per-source `last_synced` timestamp visibly on TreeCards / DetailHeader. When stale beyond a threshold (>60min for filesystem, >5min for network sources), show an amber "external state may have drifted, refresh →" hint. Honest about the limitation rather than pretending the cache is authoritative.

Probably wants a small per-source-config setting for stale thresholds; the GitHub cache is also a candidate for time-based expiry.

### D. Map density at scale

**Evidence:** `02-map-all-sources.png` is 2.4 MB and very tall — 80+ intents in a flat 2-column grid, no grouping, no filter, no visual hierarchy.

**v0.1.5 lever:** **C1 (filter/group/sort) was already in v0.1.** At this data scale it's existence-critical, not nice-to-have. Folding C1 into v0.1.5 makes more sense than landing it as a final v0.1 item then immediately polishing on top. C1 *is* part of v0.1.5.

### E. AppHeader's reversibility chip — placeholder still showing on Detail

**Evidence:** every Detail capture shows the `reversibility · 24h` chip in the AppHeader top-right.

Per A3 / `CLAUDE.md`, the workspace-refresh button (`↻ synced Xm ago`) was supposed to replace this when `onRefresh` is provided. It's still visible on Detail surfaces — either A3 didn't propagate fully, or the refresh button is conditional on something Detail doesn't satisfy.

**v0.1.5 lever:** verify A3 is fully wired through Detail. Probably a 1-line fix in `App.tsx` or `DetailSurface.tsx` — depends on where the `onRefresh` prop dies. Audit and fix.

### F. The "loading workspace…" placeholder

**Evidence:** `01-landing.png` (caught mid-load)

- Bare monospace text on warm-paper background. No glyph, no instrument identity, no progress affordance.
- Visible whenever `loadEnabledSources` is in flight: first paint, every source toggle, every refresh.
- For the GitHub source specifically, this lasts 1-2 seconds per fetch (subprocess overhead × per-issue concurrency × pagination).
- Reads as "the page is broken."

**v0.1.5 lever:** design a real loading state. Match cognitive-instrument aesthetic. Probably a small `IntegralGlyph` (like Landing uses) + a per-source progress affordance ("loading nous campaigns…" / "loading sriumcp/integral…"). Per-source progress requires the loader to surface intermediate state — currently `loadEnabledSources` is atomic, so this is a small refactor of `src/lib/sources.ts`.

### G. Sparse Detail for leaf intents

**Evidence:** `07-detail-coral-attempt.png` (fixture) + `09-detail-feature-leaf.png` (real GitHub leaf)

Both show a header card + 1-2 small bottom cards, with the bottom 60% of the page empty. The Detail surface assumes children + projections + activity exist; when they don't, the page reads as half-built.

**v0.1.5 lever:** redesign empty-state layout. For leaf intents:
- (a) Compress the layout — one card with all the info, not a stack of mostly-empty sections.
- (b) Per-kind explicit "leaf intent · details below" framing so the empty space reads as intentional.
- (c) Move the Activity Strip from right-of-Detail to inline-with-Detail when it would be empty (or when content is leaf-shaped) — reclaims horizontal space.

### H. Source picker holds up at 4 chips

**Evidence:** `04-source-picker-detail.png`

`SOURCES • demo fixture • nous campaigns • coral pi-mc • sriumcp/integral` fits comfortably on one row. Not a v0.1.5 priority. Will become one at >6 sources; deferred until then.

### I. Real-vs-fixture rendering asymmetry

**Evidence:** compare `06-detail-coral-optimization.png` (fixture, polished) vs the imagined real pi-mc Detail (sparser per the G-C gaps).

Fixture has hand-authored tags ("optimization", "evaluator"), polished summary, balanced extension card with rich tags ("island", "pop 12", "best 0.842"). Adapter output is structurally lossy: empty success_criterion (G-N-8/G-C-1/G-F-1), empty inherited_conventions (G-F-2), single `direction:maximize` tag (G-C-2 stuffing into tags) instead of structured fields.

Net: fixture intents look like the chrome was designed for them; adapter intents look like the chrome accommodates them grudgingly.

**v0.1.5 lever:**
- (a) Make adapter output denser by promoting G-* gaps that improve density (G-C-2 direction-as-extension-field, G-C-7 evaluator_feedback) — but this crosses into v0.2 schema work.
- (b) Accept the leanness and design the chrome to look intentional with sparse data — Karpathy aesthetic actually rewards this if done deliberately.

(b) is the v0.1.5 discipline. (a) is v0.2.

### J. The fixture workspace's role is shifting

**Evidence:** `03-map-fixture-only.png`

The fixture used to demo "what's possible." Now real adapters exist, the fixture's role is shifting to "test scaffold for visual regression baselines." The visual baselines hardcode `?sources=fixture` so they pin to the fixture only; this is correct discipline.

**v0.1.5 lever:** decide whether the fixture remains user-visible (current state — it shows up as a "demo fixture" chip) or becomes test-only. If user-visible: lean into "demo data" framing so users don't think it's a real source. If test-only: hide the fixture chip from the picker by default; make it a `?sources=fixture` opt-in. Probably the latter is cleaner once real adapters cover all canonical kinds.

## Suggested v0.1.5 scope (first cut, before brainstorming)

**In scope** (visible breakage worth fixing):
1. **Real loading state** to replace `loading workspace…` (theme F)
2. **Stale-data signal** on adapter sources (theme C)
3. **Empty-state design** for leaf intents + activity-strip (themes B + G)
4. **Refresh-button propagation** on Detail (theme E)
5. **Map filter / group / sort** (C1 absorbed; theme D)
6. **Visual baseline regen** as expected fallout from the above

**Out of scope** (defer to v0.2):
- Coral + GitHub projection plugins (theme A; option (a) — promotes S-1)
- Timeline events for GitHub (theme B; option (a) — promotes G-F-7/8)
- Schema bumps for any G-* gap
- New IntentKinds
- Adapter expansion (Coral writeback, etc.)
- Real-vs-fixture rendering reconciliation via schema bumps (theme I option (a))

**Borderline — needs the brainstorm:**
- Per-kind shaping buttons (`+ new coral campaign`, etc.) — strict v0.2 by current roadmap, but visible asymmetry might pull it into v0.1.5
- Projection plugin for `feature-campaign` — small cost, high visual impact
- Fixture's user-visibility (theme J)

## Open questions (the brainstorm should resolve these)

1. **Should v0.1.5 land before or after v0.1 fully ships?** Currently v0.1 is one item from done (C1). Folding C1 into v0.1.5 means v0.1 effectively ships *as* v0.1.5. Alternative: ship v0.1 with C1, then do v0.1.5 as a discrete polish phase.

2. **What's the v0.1.5 falsification criterion?** B1 + B2 had concrete stop conditions ("the schema accepts X without modification"). Polish phases don't have that. Need a substitute — probably "the same 10 captures that prompted v0.1.5 now read as deliberate" with side-by-side before/after PNGs.

3. **How much work is acceptable in v0.1.5?** A genuine polish pass (themes E + F + G) is days of work. A polish pass that absorbs C1 + theme C + theme G is 1-2 weeks. A polish pass that includes a Coral projection plugin (theme A option a) is 2-3 weeks. Need to scope.

4. **Should the fixture stay visible by default?** (Theme J.) Affects landing screen and source picker semantics.

5. **Is the cognitive-instrument aesthetic still right for adapter-output density?** Karpathy aesthetic was designed for the 4-fixture demo. With 80+ real intents the density story is different. Worth explicitly checking.
